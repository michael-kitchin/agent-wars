# Commander messages

What one side can say to another, what a commander keeps to itself, and when those words are delivered.

The engine is the authority. The symbols named below are the ones to check when this page and the code disagree. Nothing in these rules makes a message binding. A message is a claim. It does not change orders, alliances, or the match.

## What a message is

A message is one short text from one seat to one other seat. `cleanSideMessageText` collapses whitespace, strips other control characters and the invisible direction and zero-width characters of `INVISIBLE_FORMATTING_PATTERN` (so text cannot be made to read in another order on screen than it is stored), trims, and cuts the result to `SIDE_MESSAGE_MAX_CHARS` (280), counting each code point once, with no ellipsis. An empty result is not stored.

`side_messages` holds the rows. A row is `staged` or `sent`. A staged row is a draft that has not been delivered. A sent row carries the step it was delivered on (`scope`, `turn_number`, `battle_id`, `beat_number`). At most one staged row exists for a sender and a recipient. Writing another draft deletes the previous one. There is no unique index. The delete and the insert do it.

A commander sees a message only when `sideMessageVisibleTo` says so. For a commander, that is a message it sent or a message sent to it. Fog does not widen that. The chat history lists every sent message, with fog on and while the player is only observing. Within a turn the rows follow the sender's `seatOrder`, then the recipient's. The message dialog and the Reports entry for that consult list every message that commander sent.

## What a stance is

A stance is a commander's private view of one other side. The values are `SIDE_STANCES`: `hostile`, `wary`, `neutral`, `cordial`, `friendly`. Each stored stance has a reason of at most `SIDE_STANCE_REASON_MAX_CHARS` (160) characters. An empty reason is kept. No other commander is told a stance. A stance does not create an alliance. The talk prompt tells the commander to base a stance on what a side has done to it, as the loss lines in Recent Turn Notes and the Record column of the Sides table show, more than on what that side says. The orders system text does not name that column. It still says a loss line under Your Losses is the game's record that the named side's units destroyed those units, and to read the cause before calling it an attack.

`side_stances` holds one row per commander and target. `upsertSideStance` writes a row only when the stance, the reason, the trust, or the threat changed.

## Trust and threat

A commander reports two scores with each stance, each a whole number from 0 to `RELATIONSHIP_SCALE_MAX` (4). Trust is how far the commander believes what that side tells it. Threat is how dangerous the commander finds that side. `cleanRelationshipScore` keeps a valid value and returns null for anything else, so a missing or out-of-range score is stored as null and does not drop the stance. Both are stored in the `trust` and `threat` columns of `side_stances` and are as private to the commander as the stance is. No prompt shows another commander's stance, trust, or threat, whether fog of war is on or off. A commander sees its own two scores beside its own stance, in the Sides table of the talk prompt and in the stance list of the orders prompt, and `not reported` stands in for a null score. The player's match charts show every commander's reports (see [match-statistics.md](match-statistics.md)). The reply schema asks for both scores with each stance, as integers limited to 0 through 4 by an enum.

## The two stages

A wave that is about to ask for orders can start with a talk call. `buildTalkSystemText` and `buildTalkSituationText` are that call. `parseTalkReply` reads the reply. The orders call starts only after every talk call in the wave has finished, failed, or timed out. A commander still waiting on its talk round starts no orders call after Stop, New, or Load. `openTalkRound` is that wait. `speak` and `abstain` each settle a seat once.

A commander talks only when the existing consult policy is about to ask it for orders. An unread message the prompt would show, `countUnreadPromptMessages`, causes an orders consult and does not start a talk call. That holds on the world map and in a battle. A hard skip, such as a seat with no model, no key, or a battle that has already been annihilated, is not overridden by an unread message.

Both the talk prompt and the orders prompt show the messages `sideMessageVisibleTo` allows, through `readSideMessageThreads` and `formatSideMessageThreads`. A thread keeps the newest `SIDE_MESSAGE_THREAD_PROMPT_LINES` (8) lines. The orders section is `buildOrdersMessagesBlock`. In a battle between two AI commanders both also show `buildBattleTruceText` (see Agreements). Both prompts also show this commander's combat record with each other active side, counted by `readSideCombatRecords` from the loss lines in Recent Turn Notes: a Record column in the talk prompt's Sides table, and a record line under each stance in the orders section. It is a count the game made, not a message. The count uses the strategic window before the stored turn, including during a battle, and does not include the battle in progress. When the stance is cordial or friendly and that side destroyed one of this commander's units by its own attack, in close combat, or in a battle within `STANCE_CONFLICT_RECENT_TURNS` (2) turns, `formatStanceConflict` adds `Your stance toward {code} is {stance}, but {code} destroyed your units on turn {t}.` to that side's record. A line marked `(new)` is an unread message inside that window. `countUnreadPromptMessages` counts those lines. That count is what asks for an orders consult when the policy would otherwise skip. A successful orders consult marks the shown ids seen (`markSideMessagesSeen`) when the consult still belongs to the open match (`consultStillOnOpenMatch`). An older unread message stays unseen, and it does not by itself request another consult. A failed, timed-out, or replaced consult leaves the shown lines unread. An orders consult that stops at the tool budget still marks the messages it showed as read, because the model saw them.

Both system prompts carry `SIDE_MESSAGE_SOURCE_BULLETS` and `SIDE_MESSAGE_TRUST_BULLETS`. The orders copy is `sideMessageRuleBlock`. With `AGENT_WARS_DISABLE_TALK` set, the diplomacy sentence is left out. The source and trust bullets stay. A talk call that hits its own deadline records outcome `wallClock`. A stop records `cancelled`. The cached system text does not contain a turn number, a count, or a message.

The talk call uses the same model, key, provider, and reasoning as the orders call. It does not retry, and an unparseable reply is not asked for again. The commander stays silent. `requestTalk` records a `consultation` event with `stage` `talk` when the model was reached and the consult still belongs to the open match.

## Timeouts

`AI_TALK_REQUEST_TIMEOUT_MS` (60_000) bounds one talk call. `AI_TALK_ROUND_TIMEOUT_MS` (75_000) bounds the wave. A seat that has not finished when the round closes is silent. The orders calls then start. A timeout does not hold the turn past that round. `AI_CONSULTATION_WAIT_TIMEOUT_MS` includes the round. The orders tool loop still stops at `AI_CONSULTATION_WALL_CLOCK_MS` (600_000). The pool's own wall clock is that constant plus the round timeout.

In a battle, only the two sides fighting talk to each other. A battle commander can send a message to, and set a stance toward, the opposing side only, so a side outside the battle receives nothing from its beats (`readTalkPromptInput`). A battle against Neutral, or against a side that has left the match, makes no talk call and is silent with `no_recipients`. So does a battle against a human side, because only a battle between two AI commanders names the sides fighting (`battleOpponentSeatId`).

A silence reason is `abstained`, `failed`, `timed_out`, `unparsed`, `cancelled`, or `no_recipients`. None of those writes a message.

## The tables and the recording

`ensureSideMessageTables` creates `side_messages` and `side_stances` on open. They are not in `GAME_DB_REQUIRED_TABLES`. `EXPECTED_USER_VERSION` is unchanged. `resetGameForNewMatch` deletes both.

`side_stances` is copied into a history frame. `side_messages` is not. Each sent message is a `message_sent` event (`recordSideMessageSent`). Each stance change is a `stance_declared` event (`recordSideStanceDeclared`). A talk call is a `consultation` event with `stage` `talk`. The details are in [match-recording.md](match-recording.md).

## The human player's messages

`stageHumanSideMessage` stores a draft from the active human seat (`activeHumanSeatId`). The chat panel at the map's bottom-right is where the player writes that draft. Enter or the send button stages it. Staging the same side again replaces the draft. Ready sends it. A beat of a battle between two AI sides does not send them. `sendStagedHumanSideMessages` delivers the staged drafts when a strategic turn is committed (`handleGameReady`, after `recordStrategicOrders`) and when a tactical beat is committed (`IPC_GAME.commitHumanTacticalDraftOrders`, after `recordTacticalBeat`). A draft whose recipient has left the match is deleted and not sent. The recipient's next orders consult shows the message. If the policy would not have consulted that commander, the unread message still does, and that consult does not talk. A reply, when the commander sends one, arrives on a later consult. The consult that was caused only by the unread count does not talk.

The message dialog lists every message that commander sent in that consult, including while fog of war is on and while the player is only observing. Under Messages, one line per message, in `seatOrder`: `→ `, the flag, `sideDisplayName`, `: `, and the text. The first line is `1em` under the header, and the lines sit against each other. There is no bullet. The human's flag is the seat-1 badge (`createMessagePartyFlag`) and the name is that seat's nickname, or `Human` when the nickname is empty. Strategy follows when the consult sent it, `1em` under the last message line. The chat history uses the same flag and name, and it lists every sent message, including one commander to another. A battle message adds ` (battle)` after the recipient. Commanders cannot read the player's messages to other sides. An observer reads every message and cannot write. A timed-out orders consult does not open the dialog. The dialog and a filed Reports entry stay as they were when the consult was stored.

Stored and recorded text is exactly what the commander or the player wrote. The chat panel, the message dialog, and the Reports tab show a side code in that text (`h1`, `a1` to `a4`) as the side's display name, with the original text as a tooltip (`sideCodesToDisplayNames` in `src/shared/sideCodeDisplayText.ts`). Unit ids, uppercase hex codes, and codes of sides not in the match are not changed. Prompts are not changed.

## Agreements

An agreement is one AI commander's private record of what it believes it has agreed with one other side. The two sides' records may differ, and no commander sees another's record. The game never enforces an agreement: no order is blocked or changed because of one, and a commander may keep or break any agreement. The briefing does tell a commander when its units share a hex with an active pact partner (`readPactContactLines`) and when its campaign target is held by one. The engine's own choices also avoid active pact partners (`CAMPAIGN_PACT_KINDS`): the campaign target, a new campaign lift toward a target the engine picked, and the operations it launches itself. It judges who holds a city by what the commander knows (`campaignTargetHolderSeatId`). The human player keeps no agreement record, but an AI commander may record an agreement with the human seat. Agreements are made, changed, and decided on the world map only. A battle between two AI commanders shows each one its own agreements with the other side, read-only (`buildBattleTruceText`, `sideAgreementsShownInBattle`). A battle still creates, changes, and decides none, and a battle talk reply still has no `agreements` list.

The kinds are `SIDE_AGREEMENT_KINDS`: `non_aggression`, `ceasefire_in_place`, `no_entry_zone` (it names hex codes, and the store keeps their H3 indexes), `joint_action` (it names a third side in `against`), and `information_sharing`. The stored statuses are `SIDE_AGREEMENT_STATUSES`: `proposed`, `active`, `ended`, `broken_by_them`, and `broken_by_me`. The commander sets the status itself, so there is no handshake. A new agreement may start only as `proposed` or `active` (`SIDE_AGREEMENT_NEW_STATUSES`). The intents are `keep`, `opportunistic`, and `plan_to_break`.

The standing of an agreement is worked out on read by `sideAgreementStanding` and is never stored. A closed stored status is its own standing. A `proposed` or `active` agreement is `lapsed` when the other side is out of the match, otherwise `expired` when its end turn is before the current turn, otherwise its stored status. An agreement is open when its standing is `proposed` or `active`. Only an open agreement counts toward the limit, can be changed, and gets evidence, and only an `active` one accepts a decision.

The limits are `SIDE_AGREEMENT_MAX_TURNS` (10 turns from the turn the agreement is recorded, applied by `resolveSideAgreementEndTurn`), `SIDE_AGREEMENT_MAX_OPEN_PER_SIDE` (3 open agreements with any one side), `SIDE_AGREEMENT_TERMS_MAX_CHARS` (160), and `SIDE_AGREEMENT_ZONE_MAX_HEXES` (6). The contact lines list at most `PACT_CONTACT_MAX_HEXES_PER_SIDE` (6) shared hexes per partner (`src/main/sideAgreements/pactContactLines.ts`). A closed agreement (expired, lapsed, ended, or broken) stays in the commander's ledger until `SIDE_AGREEMENT_RECENTLY_CLOSED_TURNS` (2) turns after the later of its last change and its end turn, then drops out of the prompts (`buildSideAgreementViews`). An ended or broken agreement's line names the turn it closed, for example `broken by a4 on turn 4`, from the view's `closedTurn`, so the planned span in the same line is not read as the time it applied.

A strategic talk reply creates and changes agreements through its `agreements` list. `parseSideAgreementEntries` drops an entry, counting it, when it is not an object, has a bad `id`, names a side that does not resolve or is the commander's own, has a kind, status, or intent outside its list, has empty terms, has an `endTurn` that is not an integer, repeats a positive id, is a `joint_action` without a valid third side, or is a `no_entry_zone` with no hex code. `persistTalkAgreements` then applies the limits that depend on the match, inside the talk round's transaction. A new entry (`id` 0) is dropped when its side or third side is out of the match, its status is not `proposed` or `active`, the commander already holds the open limit with that side, its end turn cannot be fixed, or its zone translates to no hex. A change (a positive `id`) must name the commander's own open agreement with the same side and kind, and is dropped otherwise. It may change the terms, the zone, the end turn, the status, the intent, and the reason. An unchanged resend writes nothing and is not an event. A new entry (`id` 0) that repeats one of the commander's open agreements, with the same side, kind, third side, terms (compared without regard to case), and zone, is applied to that agreement as a change, so a commander that forgets the id adds no copy. Sending an active agreement again as `proposed`, by id or as a repeat, leaves it active; ending one takes a closing status.

A strategic orders reply may carry an optional `agreementDecisions` list (`normalizeAgreementDecisions`, `applySideAgreementDecisions`). Each entry is `{"id", "decision": "keep" or "break", "reason"}`. It is read on the world map only, and a battle reply's key is ignored. A decision is accepted only for an agreement of that commander whose standing is `active`, and any other id is answered with a drop reason. Up to `SIDE_AGREEMENT_MAX_DECISIONS` (12) are read, and a repeated id counts once. A decision is never checked against the orders, and it does not change the agreement: ending one is a status change in the next talk reply. The latest decision is stored on the agreement (`decision`, `decision_reason`, `decision_turn`), recorded as an `agreement_decision` event, and shown in the next talk prompt as `Your decision on turn {n}`.

Each open agreement is shown to its commander with the game's record of losses both ways since it began (`formatSideAgreementEvidence`), in the wording of the Record column of the Sides table, or `No turn has resolved since this agreement began.` when no turn has resolved.

`side_agreements` holds the rows. `ensureSideAgreementTable` creates it on open, it is not in `GAME_DB_REQUIRED_TABLES`, `EXPECTED_USER_VERSION` is unchanged, `resetGameForNewMatch` clears it, and it is a frame table. A save from before agreements loads with none. With talk turned off no agreement is recorded, shown, or decided.

Two recorder events carry the history, both visible only to the owning commander and with no display text: `agreement_recorded` (`recordSideAgreementRecorded`), written when an agreement is created or any stored field changes and carrying `previousStatus`, and `agreement_decision` (`recordSideAgreementDecision`). Their payloads are in [match-recording.md](match-recording.md). The charts dialog shows every commander's agreements over time, rebuilt from these events and the strategic loss events when the charts snapshot is read (see [ux/charts-dialog.md](ux/charts-dialog.md)).

The two prompts of each diplomacy call are written to `debug-last-talk-system-prompt-N.txt` and `debug-last-talk-user-prompt-N.txt` when `AGENT_WARS_LOG_FULL_PROMPTS` is on. Only the latest talk call per commander is kept. With the flag off, the debug log gets only the lengths.

## Turning talk off

`AGENT_WARS_DISABLE_TALK=1` makes `isTalkStageEnabled` false. No talk call runs, and no new talk rows are written. Stored agreements are kept and not used: no prompt shows them, none is decided, the engine ignores them (`readActivePactPartnerSeatIds`), and the battle exit rule leaves out agreeing to stop fighting. Orders consults continue. The orders system prompt still carries the message rules, so a run with talk off still pays for them. A pilot comparison of orders cost with talk on and off measures what talk adds, not what the message rules cost. The flag is read by `isEnvFlagEnabled` in `src/main/envFlag.ts`.
