# Hybrid AI (what ships)

Short description of how the LLM opponent is wired in **2.5.0**. Combat, movement, and production rules live in [combat-rules-v3.md](combat-rules-v3.md). **What the model is told today** is catalogued in [ai-commander-prompts/](ai-commander-prompts/README.md) — this page does not restate prompt copy.

The engine under `src/` wins if this file drifts.

## Player-facing picture

You supply an OpenRouter API key for each AI opponent and pick a **tool-capable** model. The opponent does not see the true board: it gets a briefing built from **its** fog (or omniscient view if fog is off), then it may call a small set of **read** tools, then it submits one JSON envelope of orders. Standing orders and an engine attack sweep carry quiet turns. You can run **event-driven** consultation (consult when callbacks or mandatory overrides fire) or consult every turn. Tactical battles use the same loop once per beat.

Each AI seat has its own doctrine. Balanced is the shared strategy list and adds no further prompt block. Aggressive and Cautious each add one block after that list, in strategic prompts and in battle prompts. Random draws one of the three when the match starts, from the match seed and the seat's order, and keeps that draw. The commander's prompt includes it. A snapshot sent to the interface leaves it null until the match is over.

The main process keeps one commander pool (`src/main/openRouter/commanderPool.ts`). Each active AI seat that has a model can be consulted at the same time when `hasKey` is true. `hasKey` is true when the legacy key is non-empty or any AI seat's `hasApiKey` flag is true. The request sends that seat's key from `readSeatApiKey`. An empty stored key does not call the model. Each seat has its own status: planning, ready, timed out, no model, or out. A consult that runs past the wall clock (`AI_CONSULTATION_WALL_CLOCK_MS`, 300000 ms) or the wait (`AI_CONSULTATION_WAIT_TIMEOUT_MS`) leaves that seat on standing orders and marks it timed out. Cost and the consultation count are stored on the seat. Ready, the post-resolution consults, and the match screen use this pool. The screen starts and stops planning through it and reads statuses once a second while the button reads Stop during planning. A finished consult's message is shown from that read. Ready does not send orders of its own. The footer and the Commanders tab show the sum of the seats' stored cost.

The console's Commanders tab holds Start or Stop, one card per commander, the tool groups, and the activity log. Each commander's API key, model, reasoning, and doctrine are on that commander's popover. A consultation uses that seat's key. An empty key means that seat does not call the model. A consult that runs before any per-seat key has been stored uses the legacy key. The button stays on Start for that match until a commander is saved, because it reads each seat's `hasApiKey` flag. The first save of a commander in that match stores the edited key on that seat and the legacy key on the other AI seats. After that map exists, a seat whose stored key is empty does not call the model. The next new game remembers those commanders from the match start, and from each later save during the match. It is not a full briefing observatory. The last run can write `debug-last-strategic-prompt-N.txt`, `debug-last-tactical-prompt-N.txt`, `debug-last-user-prompt-N.txt`, and `debug-last-openrouter-response-body-N.txt`. N is `aiIndexForSeatId` of the seat being consulted. Opponent 1 writes `debug-last-strategic-prompt-1.txt`. Those files show that run and can go stale. Formatted snapshots of one strategic prompt, one tactical prompt, and one strategic reply: [example-strategic-prompt.md](ai-commander-prompts/example-strategic-prompt.md), [example-tactical-prompt.md](ai-commander-prompts/example-tactical-prompt.md), [example-strategic-response.md](ai-commander-prompts/example-strategic-response.md).

## Layers

1. **Pre-computation** (`src/main/precomputation.ts`). Before a consult, the engine runs `assess_unit` on opponent units and `assess_hex` on relevant hexes, then `formatBriefing` / `formatTacticalBriefing` injects tables (unit status, Best Options, production, memory, standing orders, air, sealift). Combat-estimate injection was removed; Best Options carries legal this-period actions instead.
2. **Ad-hoc tools** during the consult. Listed in [ai-tools.md](ai-tools.md). When a briefing is present, assessment and estimation tools are usually omitted from the model's tool list because those facts are already in the briefing.
3. **Envelope writes.** Standing-order assign/cancel, memory write/delete, callbacks, and (strategically) production queues are applied from the parsed JSON, not from a second write-tool path — except production, which also exposes `set_build_queue` as a tool. See [ai-tools.md](ai-tools.md).
4. **Standing-order execution** at Ready / tactical beat (`generateOrdersForStandingOrders`). DEFEND auto-fires; `hold_fire` suppresses auto-fire and the tempo sweep.
5. **Tempo sweep** (`collectTempoRuleAttacks` / `collectTacticalTempoAttacks`). One legal attack for each unit that can shoot and was not already ordered. Not described to the model on purpose.

## When a consult happens

- **Every-turn mode:** Ready gathers one order set for each active AI seat (`gatherCommanderOrdersForReady`). A seat that is still planning is waited on until it leaves planning. That wait uses the consult's own deadline (`AI_CONSULTATION_WAIT_TIMEOUT_MS`). Ready does not start a second, shorter race. Stored pending orders are used and then cleared. When nothing is stored, the button reads Stop, `hasKey` is true, and the seat has a model, Ready starts that seat's consult through the pool and waits the same way. The call still uses that seat's own key, so an empty seat key stores no model orders. Otherwise that seat uses standing orders and the attack sweep. There is no post-resolution model call. A timeout clears that seat's pending orders, so the next Ready uses standing orders.
- **Event-driven mode, strategic:** each active AI seat is consulted on its own.
  - Ready uses a stored plan, waits when that seat is already planning, or falls through to standing orders and the sweep. It does not start a new consult.
  - After resolution, once playback finishes (or there is nothing to animate), one deferred entry runs `runEventDrivenAfterResolutionConsultation` for every active AI seat at the same time. Each seat shows planning while its consult runs and ready after. The pool's wall clock and wait are the deadline. When playback is not deferred, Ready waits for all of those consults before it returns. If a seat's evaluation calls the model, those orders are stored as that seat's pending orders for the next Ready. When a tactical battle is already in planning, the battle's consult was held for this consult. It starts when the result is applied, and when a stale push for another turn only clears the latch. Queue writes in that strategic result apply while the battle is open and the turn phase is planning. Ready keeps the AI wait label while that battle consult is planning. From the playback notice until the result arrives, Ready shows the AI wait label (see [resolution-playback.md](ux/resolution-playback.md)). Clicking Stop cancels these consults and stores no orders from a consult that had not finished, so the next Ready uses standing orders. Changing one seat's model retries a consult that has already started, once, with the model that is saved now. A consult that has not started is skipped. Opening New cancels them. Leaving a battle does not cancel a strategic consult that is already running.
  - The next Ready reads each seat's pending orders.
  - If a seat's evaluation does not call the model, or the call fails, that seat's pending orders are cleared and the next Ready uses standing orders. A timeout clears them too. There is no follow-up model call. A cancelled call does not clear orders that were already stored, and it does not store the cancelled reply.
  - If the deferred consult is abandoned because the playback notice does not match, the screen starts planning through the pool so the turn is not left without a plan.
- **Event-driven mode, tactical:** after each beat, `runEventDrivenAfterTacticalBeatConsultation` runs the opposing AI seat's evaluation through the pool. A Neutral opponent has no consult. A beat with no trigger does not call the model. A plan that comes back stays in the pool until the next tactical commit, which reads it from there. An empty plan starts another battle consult.
- **Draft edits:** the player's draft orders are not consult input, so editing them never cancels, restarts, or discards a consult. Only clicking Stop, a removed key or model, changing the selected model while a consult is running, an Events toggle, a new game, battle exit or reconciliation, annihilation, the wait timeout, or a rejected request cancel it. Leaving a battle stops the tactical consult and leaves a strategic one running.

Mandatory overrides (`evaluateMandatoryOverrides` in `callbackEvaluation.ts`): `first_consultation`, `first_combat`, `new_contact`, `unit_destroyed`, `unordered_unit`, `standing_order_blocked`, `attack_mix_changed`, `deadman` (5 turns, `DEADMAN_TURNS`).

Subscription events the evaluator implements: `turns`, `unit_engaged`, `unit_destroyed`, `unit_arrived`, `threat_escalation`, `infrastructure_destroyed`. **`territory_changed` is a no-op** (accepted, never fires).

Each consult **replaces** the full callback list. Tactical subscriptions use sub-unit ids and are cleared when the battle ends.

## Consult loop bounds

`requestOrdersFlow` / `requestOrdersToolLoop.ts`:

- At most `REQUEST_ORDERS_MAX_TOOL_ROUNDS` (**50**) tool rounds. While the consultation offers at least one tool, every round before the model's first tool call sends `tool_choice: required` and no envelope schema, and every later round sends `tool_choice: auto` with the schema, so the model can submit the envelope or call more tools. A provider that rejects `required` (Amazon Bedrock's Claude endpoint does) is retried once with `auto`, and that model stays on `auto` for the rest of the session; its rounds before the first tool call still carry no schema. A model whose `supported_parameters` lists `tools` but not `tool_choice` gets the tools with no `tool_choice`. A model that does not list `tools` is consulted as if every group of model-callable tools were off, so it cannot submit production orders, memory updates, or standing-order actions; the strategic briefing is still attached, and event-driven consultation still follows the Commanders tab's Events group. A consultation with no tools sends neither `tools` nor `tool_choice`, and carries the schema on every round. The repair call still refuses tools.
- One model call aborts after `AI_MODEL_REQUEST_TIMEOUT_MS` (**90_000** ms) and is retried once (`AI_MODEL_REQUEST_RETRY_COUNT`). A body that has started and then goes quiet for **15_000** ms is dropped and is not retried. The hard body timer uses the same **90_000** ms, measured from when headers arrive.
- Wall clock `REQUEST_ORDERS_MAX_WALL_CLOCK_MS` (**300_000** ms), checked before each round. The round already in flight, and the parse-repair call, can run past that mark.
- Callers wait up to `AI_CONSULTATION_WAIT_TIMEOUT_MS` (**660_000** ms): the wall clock plus those two retried calls. The commander pool uses that wait, and the wall clock, as the deadline for Ready and for post-resolution. It aborts that seat when either fires. A consult the production runner starts still has its own waiter (`executeAbortableConsult` in `src/main/ipc/modelConsultAttempt.ts`) inside that same budget. `READY_REQUEST_TIMEOUT_MS` stays **120_000** ms because event-driven consultation runs after Ready returns. Clicking Stop, changing the model, or opening New aborts every in-flight opponent call sooner. Leaving a battle aborts tactical calls only, so a strategic consult that is already running keeps going. A model change retries a deferred consult that had already started, once, with the model that is saved now.
- Malformed empty completions retry (`MALFORMED_COMPLETION_RETRY_LIMIT` = 2). Unparseable final JSON gets one repair call with tools off. A parsed envelope whose actor rows were all dropped, and whose production apply count is 0, gets that same repair call once. A repair that parses replaces the original, even when that repair's actor rows were also all dropped. A repair that does not parse leaves the original envelope in place.
- Completion budget: the model's advertised `top_provider.max_completion_tokens` on every call, at every reasoning level (`completionMaxTokensFromAdvertisedLimit`). When that limit is missing, the call uses `OPENROUTER_ORDER_FLOW_COMPLETION_MAX_TOKENS` (**8192**). A 402 that names an affordable count of at least 512 (`OPENROUTER_MIN_COMPLETION_MAX_TOKENS`), and below the request, retries at that count and remembers it for later calls. The remembered count can lower a later request, and the request is never above the chosen budget. An affordable count below 512 is not used as a cap.
- Request options are resolved once per consult (see [source-inventory.md](ai-commander-prompts/source-inventory.md) section 4.4). The saved reasoning effort goes on every request. For models that support structured outputs, a closed envelope schema plus response healing goes on every round after the first tool call, on every round of a consultation without tools, and on the repair call, but never on a round that sends `required`. Anthropic models get it too; their first schema request currently fails because the envelope schema exceeds Anthropic's schema limits, and they continue without it. Each refusal is retried once without the rejected option. These refusals are expected, so they are written to the AI activity log as ordinary lines and to `debug.log` at info level (see [ai-activity-log.md](ux/ai-activity-log.md)). The developer flag `AGENT_WARS_DISABLE_STRUCTURED_OUTPUTS=1` withholds the schema from every model for a run.

Exhausting the tool-round cap records a successful-but-empty consult and warns on the **next** system prompt.

## Writes vs reads

| Path | Used for |
| --- | --- |
| Tools | `plan_route`, `check_distance`, `assess_unit`, `assess_hex`, `estimate_combat`, `memory_read`, `query_orders`, `query_production`, `set_build_queue` |
| JSON envelope | `orders` (including `assign_order` / `cancel_order` / `explicit_move` / `ranged_attack`), `airStrikes`, `ferryOrders`, `callbacks`, `memoryUpdates`, `productionOrders`, `strategy`, `message` |

Tactical envelopes omit `assign_order`, memory writes, and production. Sub-units are ordered with `explicit_move`, `ranged_attack`, embark/disembark, `transport_move`.

A strategic consult applies `memoryUpdates` through `executeMemory` in `applyParsedMemoryUpdates` after order validation when memory tools are enabled. A rejected row is a drop reason. The consultation still succeeds. A battle consult does not apply the rows. A list sent while the memory group is off is one drop reason and is not stored.

## Coordinates

The model never sees raw H3 indexes. Briefing hex codes (and lat/lng internally) are the contract. Strategic codes name the loaded match's strategic cells and are replaced when another map loads. Tactical codes name one battle's footprint. Tool results are rewritten to hex codes by `encodeOpenRouterToolResultForLlm`.
