# Hybrid AI (what ships)

Short description of how the LLM opponent is wired in **2.5.0**. Combat, movement, and production rules live in [combat-rules-v3.md](combat-rules-v3.md). **What the model is told today** is catalogued in [ai-commander-prompts/](ai-commander-prompts/README.md) — this page does not restate prompt copy.

The engine under `src/` wins if this file drifts.

## Player-facing picture

You supply an OpenRouter API key for each AI opponent and pick a **tool-capable** model. The opponent does not see the true board: it gets a briefing built from **its** fog (or omniscient view if fog is off), then it may call a small set of **read** tools, then it submits one JSON envelope of orders. Standing orders and an engine attack sweep carry quiet turns. You can run **event-driven** consultation (consult when callbacks or mandatory overrides fire) or consult every turn. Tactical battles use the same loop once per beat.

Each AI seat has its own doctrine. Balanced, Aggressive, and Cautious each add one block after the shared strategy list. Battle prompts print that block from `buildDoctrineBlock`. A strategic prompt prints that block from `buildStrategicDoctrineBlock`. Balanced then adds one production-denial line, and cautious adds one. Aggressive stays on the shared block. On a region-versus-region consult with standing orders on, those blocks name the campaign target. Otherwise they name the nearest enemy home region. The campaign thresholds below do not change with doctrine. Random draws one of the three when the match starts, from the match seed and the seat's order, and keeps that draw. The commander's prompt includes it. A snapshot sent to the interface leaves it null until the match is over.

The main process keeps one commander pool (`src/main/openRouter/commanderPool.ts`). Each active AI seat that has a model can be consulted at the same time when `hasKey` is true. `hasKey` is true when the legacy key is non-empty or any AI seat's `hasApiKey` flag is true. The request sends that seat's key from `readSeatApiKey`. An empty stored key does not call the model. Each seat has its own status: planning, ready, timed out, no model, or out. A consult that runs past the wall clock (`AI_CONSULTATION_WALL_CLOCK_MS`, 600000 ms) or the wait (`AI_CONSULTATION_WAIT_TIMEOUT_MS`) leaves that seat on standing orders and marks it timed out. Cost, the consultation count, and think time are stored on the seat. Think time (`seats.think_time_ms`, written by `recordSeatThinkTime` and read as `thinkTimeMs`) is the launch-to-settle time of every consult the pool settles, including a timeout or a failure. A player stop and a match reset add nothing. A timeout or a zero-cost failure adds think time and does not increment `consultation_count`. The result row shows that total with `formatThinkTimeLabel`. The pool logs `commanderPool consult timed out; standing orders will run` with the seat, the turn, and the elapsed milliseconds when its own deadline fires. Ready, the post-resolution consults, and the match screen use this pool. The screen starts and stops planning through it and reads statuses once a second while the button reads Stop during planning. A finished consult's message is shown from that read. Ready does not send orders of its own. The footer and the Commanders tab show the sum of the seats' stored cost.

The console's Commanders tab holds Start or Stop, one card per commander, the tool groups, and the activity log. Each commander's nickname, API key, model, reasoning, provider, and doctrine are on that commander's popover. The nickname is the name the match shows for that side (`sideDisplayName` in `src/shared/sideNicknames.ts`). The prompt still names the side by its full `homeRegion`, not that nickname. Changing only the nickname does not cancel that seat's consult. A consultation uses that seat's key. An empty key means that seat does not call the model. A consult that runs before any per-seat key has been stored uses the legacy key. The button stays on Start for that match until a commander is saved, because it reads each seat's `hasApiKey` flag. The first save of a commander in that match stores the edited key on that seat and the legacy key on the other AI seats. After that map exists, a seat whose stored key is empty does not call the model. The next new game remembers those commanders from the match start, and from each later save during the match. It is not a full briefing observatory. The last run can write `debug-last-strategic-prompt-N.txt`, `debug-last-tactical-prompt-N.txt`, `debug-last-user-prompt-N.txt`, and `debug-last-openrouter-response-body-N.txt`. N is `aiIndexForSeatId` of the seat being consulted. Opponent 1 writes `debug-last-strategic-prompt-1.txt`. Those files show that run and can go stale. Formatted snapshots of one strategic prompt, one tactical prompt, and one strategic reply: [example-strategic-prompt.md](ai-commander-prompts/example-strategic-prompt.md), [example-tactical-prompt.md](ai-commander-prompts/example-tactical-prompt.md), [example-strategic-response.md](ai-commander-prompts/example-strategic-response.md).

Chat completions and the model-list GET identify the app to OpenRouter. Both send the headers from `openRouterAttributionHeaders` in `src/main/openRouter/openRouterAttributionHeaders.ts`: `HTTP-Referer` is `OPENROUTER_APP_HTTP_REFERER` (`https://github.com/michael-kitchin/agent-wars`), `X-OpenRouter-Title` is `OPENROUTER_APP_TITLE` (`Agent Wars`), and `X-OpenRouter-Categories` is `OPENROUTER_APP_CATEGORIES` (`game`). Those requests omit `X-OpenRouter-App-Visibility`, so OpenRouter lists the app publicly. The key stays in the `Authorization` header only ([SECURITY.md](../SECURITY.md)).

## Layers

1. **Pre-computation** (`src/main/precomputation.ts`). Before a consult, the engine runs `assess_unit` on opponent units and `assess_hex` on relevant hexes, then `formatBriefing` / `formatTacticalBriefing` injects tables (unit status, Best Options, production, memory, standing orders, air, Missile Forces when the seat has a missile and the consult is strategic, sealift). On a strategic region-versus-region consult with standing orders on, `resolveCampaignObjectiveForSeat` stores the campaign objective before that briefing is built. Combat-estimate injection was removed; Best Options carries legal this-period actions instead.
2. **Ad-hoc tools** during the consult. Listed in [ai-tools.md](ai-tools.md). When a briefing is present, assessment and estimation tools are usually omitted from the model's tool list because those facts are already in the briefing.
3. **Envelope writes.** Standing-order assign/cancel, memory write/delete, callbacks, and (strategically) production queues are applied from the parsed JSON, not from a second write-tool path — except production, which also exposes `set_build_queue` and `hire_mercenaries` as tools. Both write. See [ai-tools.md](ai-tools.md).
4. **Standing-order execution** at Ready / tactical beat (`generateOrdersForStandingOrders`). DEFEND auto-fires; `hold_fire` suppresses auto-fire and the tempo sweep.
5. **Tempo sweep** (`collectTempoRuleAttacks` / `collectTacticalTempoAttacks`). One legal attack for each unit that can shoot and was not already ordered. Not described to the model on purpose.

## When a consult happens

- **Every-turn mode:** Ready gathers one order set for each active AI seat (`gatherCommanderOrdersForReady`). A seat that is still planning is waited on until it leaves planning. That wait uses the consult's own deadline (`AI_CONSULTATION_WAIT_TIMEOUT_MS`). Ready does not start a second, shorter race. Stored pending orders are used and then cleared. When nothing is stored, the button reads Stop, `hasKey` is true, and the seat has a model, Ready starts that seat's consult through the pool and waits the same way. The call still uses that seat's own key, so an empty seat key stores no model orders. Otherwise that seat uses standing orders and the attack sweep. There is no post-resolution model call. A timeout clears that seat's pending orders, so the next Ready uses standing orders.
- **Event-driven mode, strategic:** each active AI seat is consulted on its own. A seat with no units left is still consulted, so it can set production on the cities it still holds. Losing every unit is not a knockout (`decideEndOfTurnOutcome`).
  - Ready uses a stored plan, waits when that seat is already planning, or falls through to standing orders and the sweep. It does not start a new consult.
  - After resolution, once playback finishes (or there is nothing to animate), one deferred entry runs `runEventDrivenAfterResolutionConsultation` for every active AI seat at the same time. Each seat shows planning while its consult runs and ready after. The pool's wall clock and wait are the deadline. When playback is not deferred, Ready waits for all of those consults before it returns. If a seat's evaluation calls the model, those orders are stored as that seat's pending orders for the next Ready. When a tactical battle is already in planning, the battle's consult was held for this consult. It starts when the result is applied, and when a stale push for another turn only clears the latch. Queue writes in that strategic result apply while the battle is open and the turn phase is planning. Ready keeps the AI wait label while that battle consult is planning. From the playback notice until the result arrives, Ready shows the AI wait label (see [resolution-playback.md](ux/resolution-playback.md)). Clicking Stop cancels these consults and stores no orders from a consult that had not finished, so the next Ready uses standing orders. Changing one seat's model retries a consult that has already started, once, with the model that is saved now. A consult that has not started is skipped. Opening New cancels them. Leaving a battle does not cancel a strategic consult that is already running.
  - The next Ready reads each seat's pending orders.
  - If a seat's evaluation does not call the model, or the call fails, that seat's pending orders are cleared and the next Ready uses standing orders. A timeout clears them too. There is no follow-up model call. A cancelled call does not clear orders that were already stored, and it does not store the cancelled reply.
  - If the deferred consult is abandoned because the playback notice does not match, the screen starts planning through the pool so the turn is not left without a plan.
- **Event-driven mode, tactical:** after each beat, `runEventDrivenAfterTacticalBeatConsultation` runs the opposing AI seat's evaluation through the pool. An AI-only battle runs both seats, the lead seat first (`leadPartyId`), then the other. On an AI-only battle each seat's consult is for that seat, and idle versus enemy activity comes from the owner of each sub-unit that marched, fired, or scored a kill. A Neutral opponent has no consult. A beat with no trigger does not call the model. A consult whose seat has no sub-units left in that battle, or whose remaining sub-units are only missiles, does not call the model. Both cases use `emptyRosterAbsenceReason` in `src/shared/commanderStatus.ts` after missiles are left out of the count, and both store `no_units_in_battle`. Annihilation skips the same way. An AI-only battle that has already set `aiOnlyEndReason` skips the call. A plan that comes back stays in the pool until the next tactical commit, which reads it from there. A reply that sets `exitBattle` and has no orders stays stored (`tacticalDraftAlreadyDecided`). An empty plan, with that flag absent, starts another battle consult.
- **Draft edits:** the player's draft orders are not consult input, so editing them never cancels, restarts, or discards a consult. Only clicking Stop, a removed key or model, changing the selected model while a consult is running, an Events toggle, a new game, battle exit or reconciliation, annihilation, the wait timeout, or a rejected request cancel it. Leaving a battle stops the tactical consult and leaves a strategic one running.

Mandatory overrides (`evaluateMandatoryOverrides` in `callbackEvaluation.ts`): `first_consultation`, `first_combat`, `new_contact`, `unit_destroyed`, `unordered_unit`, `standing_order_blocked`, `attack_mix_changed`, `deadman` (5 turns, `DEADMAN_TURNS`). After that list, `campaignReadyOverride` in `afterResolution.ts` appends `campaign_ready` when the campaign section below says the assembly is complete. A missile is built with `hold_fire`, so it is not an `unordered_unit`. `canHitNow` is false for a missile, so it does not count as able to shoot. A seat that launched this turn is not idle (`seatHadStrategicResolutionUnitActions`). Another seat's launch counts as observable when the target hex's controller is this seat (`enemyHadStrategicResolutionObservableActions`). A move counts as another side's action from `aiMoves[].player`. A kill uses the live unit's player, then the owner on `removedUnits`, and only then the side encoded in the unit id. A rehired unit keeps its first owner's prefix. A spent missile is not in the removed-unit lists, so it does not raise `unit_destroyed`.

Subscription events the evaluator implements: `turns`, `unit_engaged`, `unit_destroyed`, `unit_arrived`, `threat_escalation`, `infrastructure_destroyed`. **`territory_changed` is a no-op** (accepted, never fires).

Each consult **replaces** the full callback list. Tactical subscriptions use sub-unit ids and are cleared when the battle ends. An AI-only battle saves both commanders' strategic lists at the start (`stashOpponentCallbackSubscriptionsForTacticalBattle`) and, after that write returns, clears each saved seat's live list. A human battle saves and then clears the one AI seat. Each saved seat's Active Callbacks table starts empty. Each saved list is restored when the battle ends, including after a restart. A stored battle that has only one list restores that list. A null seat clears nothing. If the stash write throws, the live lists stay.

## Campaign

On a strategic `region_vs_region` consult with standing orders on, the engine keeps one objective per AI seat and points that seat's ground units at it. Battles are unchanged. Naval and air units keep their own suggestions. The objective is stored in the `campaign_objectives` row (`campaignObjectiveMemory.ts`) and is replaced once per consult, before the briefing, by `resolveCampaignObjectiveForSeat`. `campaignPlanForState` then builds the plan the briefing builders receive. Between consults the units follow their standing orders. The briefing asks the model to copy each Campaign Orders row into `assign_order`. Campaign Orders also lists a home defender whose standing order is a march to the target or the staging hex, with `defend` on its own hex as the new order. A campaign unit with no standing order gets that campaign order as its Suggested Destination, unless the unit is embarked infantry or armor, which gets none, or it can march onto an enemy this turn, in which case it keeps the contact march. A holding unit's order is `defend` on its own hex. A new match deletes the row. A missing row is no campaign, and the next consult picks one.

Ground units are that seat's infantry and armor, mercenaries included, units aboard a carrier excluded. **Home defenders** come from `chooseHomeDefenders`. A threat is a visible infantry or armor unit of an active enemy seat, embarked or not, within `CAMPAIGN_HOME_DEFENSE_RADIUS` (3) hops of a ground unit standing in the seat's own home. Each enemy unit is one threat, and air, naval, and missile units are not threats. The engine keeps one home unit per threat, picking home units within that radius of a threat, nearest first and then by unit id. It never keeps more than `CAMPAIGN_HOME_DEFENDER_MAX_SHARE` (half) of the seat's ground units, rounded down, so a seat with one ground unit keeps no defender. `homeDefenseCapped` is true only when that share, rather than the threat count, left a home unit out. A unit **in contact** has a visible active enemy within `CAMPAIGN_CONTACT_RADIUS` (1) hop. Home defenders and units in contact are not campaign units. Every other ground unit that can reach the waypoint by land is a campaign unit. The waypoint is the staging hex during `assemble` and the target during `assault`. During `assemble`, a campaign unit already within `CAMPAIGN_MASS_RADIUS` (2) hops of the staging hex holds: its order is `defend` on its own hex. Any other campaign unit marches to the waypoint. Best Options gives that unit `advance` rows toward the waypoint, unless an enemy-occupied hex is already a legal destination this turn. A visible enemy that is not a legal destination this turn does not redirect it. What the model is told is in [strategic-prompt.md](ai-commander-prompts/strategic-prompt.md).

Candidate cities are hexes with `urbanHexCount` greater than zero whose known controller is an active enemy seat (`knownCampaignCities`). Urban count is public. On an explored hex, control and fortifications come from the snapshot. An unexplored hex inside exactly one active enemy home counts as held by that seat, with no fortification penalty. Any other unexplored hex is not a candidate. An unexplored hex in more than one enemy home is not a candidate. An explored hex in more than one home uses its known controller. Neutral and knocked-out sides are never targets. Distance is land steps from `getLandStepDistances` over `canLandUnitTraverseEdge`. The engine picks a target only within `CAMPAIGN_MAX_LAND_STEPS` (12). The score is urban count times 2 when the hex is inside an active enemy home, otherwise times 1, divided by `(steps + 2)` times `(1 + known fortified cells / 4)`. The highest score wins. Ties go to fewer steps, then the lower H3 index. Those weights are `CAMPAIGN_ENEMY_HOME_WEIGHT` and `CAMPAIGN_FORTIFICATIONS_PER_PENALTY_STEP` in `campaignTargetSelection.ts`.

The staging hex is a land hex the seat controls and the force can reach, at least `CAMPAIGN_STAGING_MIN_STEPS` (2) land steps from the target. The nearest such hex to the target wins. Ties go to fewer steps from the force, then the lower H3 index. With none, the staging hex is null and the phase is `assault` from the start. A kept objective keeps its staging hex while the seat still controls it.

The assault threshold is `min(CAMPAIGN_ASSAULT_MIN_UNITS, own ground units)`, and at least 1. `CAMPAIGN_ASSAULT_MIN_UNITS` is 6. `assemble` becomes `assault` when that many ground units are within `CAMPAIGN_MASS_RADIUS` hops of the staging hex. `assault` falls back to `assemble` when fewer than half that threshold, rounded up, are within that radius of the staging hex or the target. A new target starts in `assemble`, or in `assault` when there is no staging hex. A stored target is kept while it is still a candidate and its land steps are at most `CAMPAIGN_REACH_LIMIT_STEPS` (30). It is replaced when it is taken, no longer an enemy city as far as the seat knows, destroyed, or farther than that. There is no timeout.

`campaignReadyOverride` returns `campaign_ready` after resolution when standing orders are on, the match is region versus region, the stored phase is `assemble`, and enough ground units stand within `CAMPAIGN_MASS_RADIUS` of the staging hex. That consult is what starts the assault. Orders off does not consult, because the phase only advances on an orders-enabled consult.

`applyCampaignTargetOverride` runs after a strategic envelope names `campaignTarget`. A code equal to the stored target changes nothing, including the phase. A different code is stored when it is a known enemy city within `CAMPAIGN_REACH_LIMIT_STEPS`. The new objective starts in `assemble`, or in `assault` when no staging hex qualifies, with source `commander`. An unknown or unreachable code is a drop reason and leaves the stored objective. The briefing for the turn that sent the field still shows the previous target.

Fortification stays legal on every city. The prompt's Exposed column and the production coaching use `listExposedCityHexes`: a city is exposed when a visible or remembered active enemy is within `PRODUCTION_EXPOSED_RADIUS` (4) hops. A remembered row with no owner counts. Neutral units and knocked-out sides do not.

Production priorities name one builder each for a missile, a naval unit, and credits. The naval line is omitted once the count reaches `Math.ceil(naval cap * NAVAL_PRIORITY_CAP_SHARE)` (`NAVAL_PRIORITY_CAP_SHARE` is 0.5). The credits line names the smallest city whose urban cells are at least `CREDITS_CITY_MIN_URBAN_PER_SIZE` (12) times `GAME_SIZE_MULTIPLIER`, and it is omitted when the treasury is at least that floor times `CREDITS_TREASURY_CEILING_TURNS` (10). A raise attention line is affordable at the fee plus `MERCENARY_UPKEEP_RESERVE_TURNS` (3) times that option's upkeep. The raise table counts enemy units within `RAISE_OPTIONS_ENEMY_RADIUS` (2) and marks a chokepoint at `CHOKEPOINT_MAX_PASSABLE_NEIGHBORS` (3) or fewer passable neighbors. The sentences those symbols print are in [ai-commander-prompts/](ai-commander-prompts/README.md).

## Consult loop bounds

`requestOrdersFlow` / `requestOrdersToolLoop.ts`:

- At most `REQUEST_ORDERS_MAX_TOOL_ROUNDS` (**20**) tool rounds. Hitting that cap sends one more call with tools withheld: the tool list stays and `tool_choice` is `none` when the model accepts it, and neither is sent when it does not. That call's text is parsed like any other final reply, and a reply that still asks for a tool is not executed. The next situation message carries the tool-budget warning whether or not the call produced orders. The call is skipped when the wall clock has already passed, and that skip still sets the warning. A cancellation does not set it. While the consultation offers at least one tool, every round sends `tool_choice: auto` and the envelope schema, so the model can submit the envelope or call tools. A model whose `supported_parameters` lists `tools` but not `tool_choice` gets the tools and the schema with no `tool_choice`. A model that does not list `tools` is consulted as if every group of model-callable tools were off, so it cannot submit production orders, memory updates, or standing-order actions; the strategic briefing is still attached, and event-driven consultation still follows the Commanders tab's Events group. A consultation with no tools sends neither `tools` nor `tool_choice`, and carries the schema on every round. The repair call still refuses tools.
- One model call aborts after `AI_MODEL_REQUEST_TIMEOUT_MS` (**180_000** ms) and is not sent again. A thrown socket or connection error, and HTTP 408, 429, 502, 503, and 504, are sent once more (`AI_MODEL_REQUEST_RETRY_COUNT`). HTTP 500 is not. A body that has started and then goes quiet for **15_000** ms is dropped and is not retried. The hard body timer uses the same **180_000** ms, measured from when headers arrive.
- Wall clock `REQUEST_ORDERS_MAX_WALL_CLOCK_MS` (**600_000** ms), checked before each round. The round already in flight, the final orders call, and the parse-repair call, can run past that mark. The final orders call is not started once the mark has passed.
- Callers wait up to `AI_CONSULTATION_WAIT_TIMEOUT_MS` (**1_320_000** ms): the wall clock plus the in-flight round and the repair call, each of which can be sent twice when the failure is a network error or a retryable HTTP status. A timeout is not sent twice. The budget still covers the longer case. The commander pool uses that wait, and the wall clock, as the deadline for Ready and for post-resolution. It aborts that seat when either fires. A consult the production runner starts still has its own waiter (`executeAbortableConsult` in `src/main/ipc/modelConsultAttempt.ts`) inside that same budget. `READY_REQUEST_TIMEOUT_MS` stays **120_000** ms because event-driven consultation runs after Ready returns. Clicking Stop, changing the model, or opening New aborts every in-flight opponent call sooner. Leaving a battle aborts tactical calls only, so a strategic consult that is already running keeps going. A model change retries a deferred consult that had already started, once, with the model that is saved now.
- Malformed empty completions retry (`MALFORMED_COMPLETION_RETRY_LIMIT` = 2). Unparseable final JSON gets one repair call with tools off. A parsed envelope whose actor rows were all dropped, and whose production apply count is 0, gets that same repair call once. A repair that parses replaces the original, even when that repair's actor rows were also all dropped. A repair that does not parse leaves the original envelope in place.
- Completion budget: the model's advertised `top_provider.max_completion_tokens` on every call, at every reasoning level (`completionMaxTokensFromAdvertisedLimit`). When that limit is missing, the call uses `OPENROUTER_ORDER_FLOW_COMPLETION_MAX_TOKENS` (**8192**). A 402 that names an affordable count of at least 512 (`OPENROUTER_MIN_COMPLETION_MAX_TOKENS`), and below the request, retries at that count and remembers it for later calls. The remembered count can lower a later request, and the request is never above the chosen budget. An affordable count below 512 is not used as a cap.
- Request options are resolved once per consult (see [source-inventory.md](ai-commander-prompts/source-inventory.md) section 4.4). The saved reasoning effort goes on every request. The saved provider choice (`throughput`, `price`, `latency`, or `nitro`) goes on every request through `applyProviderSortToChatBody`. Each consult that reaches the tool loop writes one info line, `consult telemetry`, from `logConsultTelemetrySummary` (`src/main/openRouter/consultTelemetry.ts`). The object has seatId, turnNumber, theater, battleId, modelId, providerSort, outcome, error, cancelReason, wallClockMs, toolRounds, modelCalls, timeouts, streamStalls, wallClockExceeded, servedBy, failedOn, inputTokens, outputTokens, costUsd, cachedTokens, cacheWriteTokens, fallbacks, and attempts. `cancelReason` on that line is null. `modelCalls` counts sends that started. A cancel before a send starts adds no attempt. `retried` is true only when another send follows. A network retry, an HTTP-status retry, a credit-cap retry, a required-tool-choice retry, a structured-output retry, a cache-breakpoint retry, a joined-situation retry, and a final orders call are listed in `fallbacks` only when that next send starts. Each send that started also writes a debug line, `openRouter chat attempt`. A timeout, a stream stall, a socket error, or a cancel after the send started records `provider: null` on that attempt. A consult that returns before the tool loop (no key, no model, or an empty roster) does not write the telemetry line. The pool still records think time when those seats settle. `throughput`, `price`, and `latency` send `provider: { sort }` with that value. `nitro` appends `:nitro` to a model id that has no `:`, and that request sends no `provider` field. A model id that is missing, empty, or already contains `:` keeps that id and sends `provider: { sort: 'throughput' }`. For models that support structured outputs, a closed envelope schema plus response healing goes on every tool round, on every round of a consultation without tools, on the repair call, and on the final orders call. Anthropic models get it too; their first schema request currently fails because the envelope schema exceeds Anthropic's schema limits, and they continue without it. Each refusal is retried once without the rejected option. These refusals are expected, so they are written to the AI activity log as ordinary lines and to `debug.log` at info level (see [ai-activity-log.md](ux/ai-activity-log.md)). The developer flag `AGENT_WARS_DISABLE_STRUCTURED_OUTPUTS=1` withholds the schema from every model for a run. The system message is the stable prefix. Requests whose model id starts with `anthropic/` or `google/` mark that message for caching. The consult log includes `cachedTokens`.

Hitting the tool-round cap sends the final orders call and warns on the **next** situation message, including when that call submits orders. The call is skipped when the wall clock has already passed; that skip still sets the warning and finishes with no orders. A cancellation fails the consult and does not set the warning.

## Writes vs reads

| Path | Used for |
| --- | --- |
| Tools | `plan_route`, `check_distance`, `assess_unit`, `assess_hex`, `estimate_combat`, `memory_read`, `query_orders`, `query_production`, `set_build_queue`, `query_mercenaries`, `hire_mercenaries` |
| JSON envelope | `orders` (including `assign_order` / `cancel_order` / `explicit_move` / `ranged_attack`), `airStrikes`, `ferryOrders`, `missileLaunches` when the commander has a missile and the consult is strategic, `callbacks`, `memoryUpdates`, `productionOrders`, `strategy`, `message`, and optional `campaignTarget` on a strategic region-versus-region consult with standing orders on |

Tactical envelopes omit `assign_order`, `missileLaunches`, memory writes, and production. Sub-units are ordered with `explicit_move`, `ranged_attack`, embark/disembark, `transport_move`.

An explicit_move onto the unit's current cell is held. It is not a drop, the unit stays put, and a standing order is not cancelled. The same already-arrived case in a battle is held the same way. A tactical move shortened onto the sub-unit's firing cell stays a drop. When standing orders are on, a strategic explicit_move past this turn's budget becomes a standing march (`convertOverBudgetExplicitMoveToMarch` in `src/main/openRouter/explicitMoveMarch.ts`) when a route of at least two turns exists and the first step is legal. That first step is this turn's move. Air, missiles, an invalid distance, an armor halt, and a blocked land route are not converted. When standing orders are off, that farther move is dropped.

A strategic consult keeps `get_map` and `rules` when planning tools are on. `get_map` draws the disk around a briefing code, clipped to the loaded strategic cells. In a battle the same tool is clipped to the battle footprint. See [ai-tools.md](ai-tools.md).

A strategic consult applies `memoryUpdates` through `executeMemory` in `applyParsedMemoryUpdates` after order validation when memory tools are enabled. A valid persistent write at capacity is stored, and the oldest persistent note for that seat is deleted. A stored write at capacity, and any other rejected row, is a drop reason. The consultation still succeeds. A battle consult does not apply the rows. A list sent while the memory group is off is one drop reason and is not stored.

## Coordinates

The model never sees raw H3 indexes. Briefing hex codes (and lat/lng internally) are the contract. Strategic codes name the loaded match's strategic cells and are replaced when another map loads. Tactical codes name one battle's footprint. Tool results are rewritten to hex codes by `encodeOpenRouterToolResultForLlm`.
