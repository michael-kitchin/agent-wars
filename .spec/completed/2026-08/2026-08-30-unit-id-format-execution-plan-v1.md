## Goal

Replace the current verbose unit identifiers with a short, segmented grammar so that prompts sent to the LLM carry far fewer tokens, without changing any player-facing **display name**.

| Kind | Example today | Example after |
| --- | --- | --- |
| Seeded strategic unit | `opponent-air-5` | `a1-a5` |
| Produced strategic unit | `opponent-armor-prod-7-308` | `a1-t14` |
| Tactical sub-unit | `human-naval-1:01` | `h1-n1-s1` |

Display names (`1st Infantry`, `VIII Armored`, `II Squadron (02)`) are **out of scope** and must not change.

---

## Frozen decisions

Decided by the project owner. Do not re-litigate these, and do not "improve" them mid-implementation.

1. **Segmented, not opaque.** Identifiers keep readable segments so the side and the unit type stay visible in prompts and in logs.
2. **Sub-units use an `-s` segment**, not the current `:` delimiter.
3. **Hard cutover, no data migration.** Databases created before this change keep their old identifiers. Old identifiers must keep working forever as plain opaque strings. Nothing rewrites them.
4. **Existing test fixtures are left alone.** Roughly 450 hardcoded old-format identifiers live across 44 test files. They are opaque handles as far as the runtime is concerned, and they must keep passing. Change a test only when it asserts identifier *generation*, an identifier-*derived* display name, or an ordering that this work deliberately changes.
5. **No strict format validator.** Do not add a `CHECK` constraint, a type guard, or a schema `pattern` that rejects non-conforming identifiers. That would break decisions 3 and 4.
6. **A dedicated ordinal counter.** The number in an identifier comes from a new per-player-per-type sequence, not from `display_order`. In practice the two numbers agree, but the identifier counter must never be able to hand out a duplicate.
7. **Numeric-aware ordering for LLM-facing lists only.** The four sorts that shape prompt content move to numeric-aware collation. Combat tie-break sorts keep byte-for-byte `localeCompare` so unit resolution order carries no new risk.
8. **Identifier *parsing* is consolidated in the shared layer.** Glyph and label mapping stays where it already lives.
9. **Prompt teaching examples are updated** to the new grammar, so the model imitates the right shape.

## The grammar (authoritative)

```text
strategicUnitId   = playerCode "-" typeCode ordinal
tacticalSubUnitId = strategicUnitId "-s" slot

playerCode = ("h" | "a") index
typeCode   = "i" | "t" | "n" | "a"
index      = positive integer, no leading zeros
ordinal    = positive integer, no leading zeros
slot       = positive integer, no leading zeros
```

**Player codes**

| DB `player` value | Code | Notes |
| --- | --- | --- |
| `human` | `h1` | The index is present for symmetry and future multi-human support |
| `opponent` | `a1` | Future additional AI players take `a2`, `a3`, … |

**Unit type codes**

| DB `unit_type` value | Code | Mnemonic |
| --- | --- | --- |
| `infantry` | `i` | infantry |
| `armor` | `t` | tank |
| `naval` | `n` | naval |
| `air` | `a` | air |

**Reserved letter:** `s` must never become a unit type code or a player code letter. The sub-unit segment is `-s<slot>`, and reusing `s` would make parsing ambiguous. Put this constraint in the orienting comment on the type-code table and assert it in a test.

**Worked examples**

- `h1-i1` — the human player's 1st infantry formation.
- `a1-a44` — AI player 1's 44th air formation.
- `h1-t3-s2` — sub-unit 2 of the human player's 3rd armor formation.

**No zero padding anywhere.** `h1-n1-s1`, not `h1-n1-s01`.

| Symbol | Kind | Behavior |
| --- | --- | --- |
| `UnitIdOwner` | type | `'human' \| 'opponent'` |
| `StrategicUnitIdParts` | type | `{ readonly player: UnitIdOwner; readonly unitType: BuildUnitType; readonly ordinal: number }` |
| `TacticalSubUnitIdParts` | type | `{ readonly parentUnitId: string; readonly slot: number }` |

| `formatTacticalSubUnitId(parentUnitId, slot)` | function | Builds `` `${parentUnitId}-s${slot}` `` |
| `parseStrategicUnitId(unitId)` | function | Returns `StrategicUnitIdParts` or `null` |
| `parseTacticalSubUnitId(unitId)` | function | Returns `TacticalSubUnitIdParts` or `null` |
| `unitTypeFromUnitId(unitId)` | function | Returns `BuildUnitType` or `null`; understands new **and** legacy identifiers |
| `compareUnitIdsNaturally(a, b)` | function | Total-order comparator that sorts embedded numbers numerically |

**Regexes.** Define each one **once**, at module scope, as a `const`, with an orienting comment. Do not inline regex literals at call sites.

```ts
const STRATEGIC_UNIT_ID_PATTERN = /^([ha])(\d+)-([itna])(\d+)$/;
const TACTICAL_SUB_UNIT_ID_PATTERN = /^(.+)-s(\d+)$/;
```

**Behavior to implement and test:**

- `formatStrategicUnitId` and `formatTacticalSubUnitId` **throw** on an ordinal or slot that is not a positive integer. A silently clamped or `NaN` ordinal would produce a corrupt primary key. Document the exception in the orienting comment.
- `parseStrategicUnitId` returns `null` for a leading zero in either number (`h01-i1`, `h1-i01`), for a zero or negative ordinal, and for every legacy identifier (`human-infantry-1`, `opponent-armor-prod-7-308`).
- `parseStrategicUnitId` maps only `h` to `human` and `a` to `opponent`. Any other index (`a2`, `h2`) has no corresponding DB `player` value today, so return `null` and leave a comment marking this as the multi-AI-player extension point.
- `parseTacticalSubUnitId('h1-t3-s2')` returns `{ parentUnitId: 'h1-t3', slot: 2 }`, and must never match a strategic identifier. `h1-a4` has no `-s` segment, and no type code is `s`, so this holds by construction — assert it in a test.
- `unitTypeFromUnitId` tries `parseStrategicUnitId` first, then falls back to the legacy substring checks (`-infantry-`, `-armor-`, `-naval-`, `-air-`), then tries the parent of a sub-unit identifier, then returns `null`. This is the single home for identifier-to-type inference; section 6 rewires the renderer to it.

**`compareUnitIdsNaturally` must be a total order.** Build it from a module-scope collator and add a deterministic tie-break, because a collator alone can report two distinct strings as equal and make sorts unstable:

```ts
const NATURAL_UNIT_ID_COLLATOR = new Intl.Collator('en', { numeric: true });

export function compareUnitIdsNaturally(a: string, b: string): number {
  const collated = NATURAL_UNIT_ID_COLLATOR.compare(a, b);
  if (collated !== 0) return collated;
  return a < b ? -1 : a > b ? 1 : 0;
}
```

Use `'en'` explicitly rather than `undefined`, so ordering does not vary with the host locale. Do **not** use `sensitivity: 'base'` here; it would collapse identifiers that differ only by case.

**Leave `NATURAL_ID_COLLATOR` in `src/shared/unitDisplayNames.ts` alone.** It uses `sensitivity: 'base'` and its behavior is pinned by 88 display-name test cases. Consolidating the two is a tempting reuse win and a needless regression risk. Add a one-line comment on the new comparator noting the deliberate split.

### Create `src/shared/unitIds.test.ts`

Test contracts, not internals:

- Round trip: `parseStrategicUnitId(formatStrategicUnitId(x))` equals `x`, for one unit of each of the four types, for both players.
- Round trip for sub-units, including a two-digit slot.
- Rejection of legacy shapes, zero-padded numbers, and the empty string.
- No padding: `formatTacticalSubUnitId('h1-n1', 1)` is exactly `'h1-n1-s1'`.
- Throwing on a zero, negative, or fractional ordinal.
- `parseTacticalSubUnitId` returns `null` for every strategic identifier, and specifically for one of each type code — this is the test that guards the reserved `s` letter.
- `unitTypeFromUnitId` resolves `h1-t3`, the legacy `human-armor-2`, and the sub-unit `h1-t3-s2` all to `'armor'`, and returns `null` for `'nonsense'`.
- `compareUnitIdsNaturally` sorts `h1-i2` before `h1-i10`, and returns a non-zero result for two distinct strings.

## Known hazards

| Hazard | Why it bites | Mitigation |
| --- | --- | --- |
| Stale `dist/` | The test runner walks `dist/`, so deleted or renamed tests keep passing | `npm run clean:dist` starts every gate |
| Stale `static/renderer.js` | The bundle embeds compiled copies of the identifier regexes | `npm run build:renderer` in the final gate |
| Source-text contract tests | `rendererConsolidation.test.ts` greps `renderer.ts` for a function name and for a literal line of its body; `tsc` cannot see this | Section 6 names the three affected assertions and what to do with each |
| Duplicate identifiers | A counter that returns a fallback value on a closed database would violate the `units.id` primary key | The new allocator throws instead of returning `1` |
| Reset reissuing ordinals | Clearing the counter could collide with surviving rows | `resetGameForNewMatch` already runs `DELETE FROM units` first |
| Sub-unit parsing ambiguity | A type code of `s` would make `-s<slot>` unparseable | `s` is reserved; a test asserts no strategic identifier parses as a sub-unit |
| Mixed-format rosters | A legacy save that produces a new unit holds both formats at once | Every parser keeps a legacy branch; section 6 adds a mixed-roster test; section 10 adds a manual check |
| Legacy saves generally | Old identifiers persist in `.db` files and in stashed callback subscriptions | Nothing rewrites stored identifiers |
| Unstable sort | A collator can report distinct strings as equal | `compareUnitIdsNaturally` adds a deterministic tie-break and pins the locale to `'en'` |
| Combat ordering drift | Changing tie-break sorts would shift RNG consumption | Section 7 changes only the four prompt-facing sorts and lists the ones to leave alone |
| Test fixture churn | Roughly 450 old-format identifiers across 44 test files | The runtime treats identifiers as opaque strings, so only generation, display-derivation, and intended-ordering tests change |
| Shared-layer logging | Importing `src/main/logger` into `src/shared/` breaks the renderer bundle | The new shared module has no logging; callers log at their boundary |
| Oversized `renderer.ts` | Already past the 1000-line hard limit | The section 6 edit removes more lines than it adds |
